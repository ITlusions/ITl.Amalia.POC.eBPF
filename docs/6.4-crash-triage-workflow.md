# 6.4 Crash Triage Workflow

From a crash on a monitored testlab host back to its root cause, with the standard that governs each phase and the part of this repo that supports it. The machine-readable version is in `workflows/crash-triage.workflow.json`.

**Scope:** RoE-ITlusions-Testlab-2026 (valid 2026-04-27 to 2026-12-31), ITlusions-owned or managed testlab systems only. Standards are listed from memory of their usual scope; confirm the current revision before citing one in a report.

Status values: **implemented**, **partial**, **planned**, **external** (done outside the sensor).

## Phases in detail

### 0. Authorization and scope
Confirm the RoE is valid and the target is in scope before any collection or reproduction.
- **Controls (planned):** RoE load and expiry check, CIDR target validation, operator identity binding. Defined in `7.1-dataflow-and-enforcement-points.md` and `7.3-mitigation-checklist.md`.
- **Gap:** none of these exist in code yet.

### 1. Detection and capture
Record signal, pid, fault address, instruction pointer and time.
- **Tools:** `CrashDetector.process_crash_event`; `sensor.bpf.c` for process lineage.
- **Gap:** `sensor.bpf.c` has no signal or crash hook, so the detector has no kernel event source.

### 2. Evidence preservation
Keep the coredump, memory map and binary identity before state is lost.
- **Tools:** `enable_coredumps`, `_find_coredump`, `_read_memory_maps`.
- **Gaps:** no file hashing or chain of custody; no build-id capture at exec time.

### 3. Initial triage
Classify by signal and memory region, assign a risk level.
- **Tools:** `triage_crash`, `_map_rip_location`. Scoring weights signal type, crash region, prior network activity and coredump availability.

### 4. Deduplication
Group crashes with the same normalized stack so each bug is analysed once.
- **Gap:** no stack hashing or bucket store.

### 5. Provenance correlation
Link the crash to process lineage and the last network data the process received.
- **Tools:** process and network events, IP analyzer, Sigma-Lite, `ThreatCorrelator`.
- **Gaps:** no receive hook; payload capture is a stub and byte counters are not filled; inbound connections record the pid from softirq context, which can be wrong; no socket cookie to tie a connection to a process.

### 6. Root-cause analysis
Find the faulting function and defect class.
- **Tools:** `analyze_crash` with per-signal analysis, `_unwind_stack`.
- **Gaps:** no kernel-side user stack capture; no symbolization against build-ids.

### 7. Controlled reproduction
Confirm the cause in an isolated lab, only against in-scope targets.
- **Tools:** `POCBuilder`, `examples/vulnerable-test-app`.
- **Controls (planned):** target validation before each iteration, scope tag in generated artefacts, per-iteration audit log.
- **Gap:** `POCBuilder` has no scope validation or audit trail. Do not run it until the Tier 1 controls in the mitigation checklist are in place.

### 8. Impact and prioritization
Rate severity and likelihood. The correlator gives a verdict; CVSS or SSVC scoring is done by hand.

### 9. Containment and mitigation
Patch, configuration change or interim filter on the affected system. The sensor has no enforcement or virtual patching arm.

### 10. Reporting and disclosure
- **Tools:** `export_crash_report`, `BrainCellWebSocketClient` (incidents and vulnerability reports), `AmaliaExporter.export_threat_verdict`.
- **Gap:** no CSAF or VEX output.

### 11. Verification and lessons learned
Confirm the fix and update detection content.
- **Tools:** YARA rules manager, Sigma-Lite chains, `build/test_setup.sh`.
- **Gap:** no automated regression harness for crash cases.

## Telemetry to verdict workflow

The everyday pipeline that feeds phases 1 and 5 is described in `workflows/telemetry-detection.workflow.json`: install and verify, load and configure, kernel collection, poll and parse, the four detection layers, export, and run mode.
